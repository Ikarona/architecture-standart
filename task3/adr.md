### <a name="_3bfxc9a45514"></a>**Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Клиент (Сайт) / Кол-центр | Подача заявки на сайте | Клиент смотрит список депозитов → вводит ФИО и телефон → создаётся заявка → она поступает в систему КЦ для прозвона и уточнения условий. |

| 4 | Бэк-офис кредитов | Спецставки | По запросу БО депозитов предоставляет входные данные по риску для расчёта спецставки (без доступа к данным друг друга). |
| 5 | СМС-шлюз / Телеком | Оповещения | Клиент получает СМС о подтверждённой ставке и об открытии депозита. |

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность 99.9% и режим 24/7 для ИБ/оповещений; возможность работы из резервного ЦОД, балансировка нагрузки. |
| 2 | Исключить новые прямые синхронные вызовы ИБ к БД АБС; декоуплинг через промежуточные сервисы/очереди/буферы. |

### <a name="_qmphm5d6rvi3"></a>**Решение**


**Диаграмма C4 — Контекст** (`Task3_C4_Context_MVP.png`)  
Показывает взаимодействие внешних акторов (клиент сайта, клиент ИБ, кол-центр), фронтов (Site/IB), оркестратора, шины сообщений/буфера, адаптера АБС, самой АБС, СМС-шлюза и телеком-оператора.  
Ключевые идеи:
- **Deposit Orchestrator** — анти-corruption слой, единый API для фронтов и КЦ; не даёт нагружать АБС прямыми вызовами.
- **Messaging (Kafka/буфер)** — асинхронное взаимодействие между оркестратором и **ABS Adapter**.
- **ABS Adapter** — безопасное обращение к PL/SQL-процедурам АБС, идемпотентность, ретраи.
- **Rates Store** — операционное хранилище ставок (перенос из Excel), источник персонализации.

**Диаграмма C4 — Контейнеры** (`Task3_C4_Containers_MVP.png`)  
Детализирует основные контейнеры: **InternetBank (ASP.NET MVC)**, **Site (PHP/React)**, **Deposit Orchestrator (.NET 6/Spring Boot)**, **Rates Store (MS SQL)**, **Messaging (Kafka/буфер)**, **ABS Adapter (service)**, **ABS (Oracle/PLSQL)**, **SMS Gateway**, **Call Center System**.  
Потоки:
- Site/IB → Orchestrator (создание заявок, чтение справочников и ставок).
- Orchestrator → Rates Store (операционные данные ставок; кеши для быстрого отклика).
- Orchestrator → Messaging → ABS Adapter → ABS (команды/события по открытию депозита).
- Orchestrator → SMS Gateway (уведомления клиенту).
- Call Center System ↔ Orchestrator (онлайн-обработка заявок и спецусловий).

**Логика выбора**
- Декоуплинг ИБ от БД АБС снижает риски перегрузки Oracle и повышает отказоустойчивость.
- Асинхронные потоки позволяют выдерживать пики и учитывать вертикальные ограничения АБС.
- Выбор .NET/Java + MS SQL/Oracle соответствует текущей экспертизе и снижает риски внедрения.
- Перенос ставок из Excel в управляемое хранилище обеспечивает персонализацию, аудит и версионность.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1) **Прямые API к АБС** — минимум новых сервисов, но сильная связность и риск перегрузки/недоступности.  
2) **Расширить АБС как единый API** — долгие сроки и зависимость от вертикального масштабирования Oracle.  
3) **Только файл-интеграции** — просто по внедрению, но большие задержки и слабая наблюдаемость.

**Недостатки, ограничения, риски**

- Появляется новый слой (Orchestrator/Adapter) → затраты на поддержку и мониторинг.  
- Консистентность MS SQL ↔ Oracle — нужна идемпотентность, ретраи/саги, жёсткие корреляционные ID.  
- При отсутствии Kafka на старте временный буфер ограничит масштаб и наблюдаемость.  
- Тонкая настройка ролей/прав (депозиты/кредиты) в Rates Store для соблюдения требований безопасности.
